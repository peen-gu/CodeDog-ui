# 双形态组件

不是把一套视觉缩放重排，而是**同一个组件内部渲染两套结构**，运行时按终端切换。

## 为什么要这么做

手机上「从底部升起的抽屉」可达性好、拇指易命中；PC 上「居中模态」符合桌面软件预期。把移动端的模态照搬到 PC，27 英寸屏幕中央会浮着一条窄窄的容器——技术上没错，体验上错了。

## 形态对照

| 组件 | 移动端 | PC |
|---|---|---|
| `cd-dialog` | 底部抽屉 | 居中模态 |
| `cd-select` | 底部动作面板 | 下拉面板 |
| `cd-drawer` | 底部滑入 | 右侧滑入（`auto` 时） |
| `cd-table` | 卡片列表（首列升格为标题） | 多列表格 |
| `cd-pagination` | 上一页 / 下一页 | 完整页码 |
| `cd-date-picker` | 系统原生滚轮 | 自研日历面板 |
| `cd-time-picker` | 系统原生滚轮 | 双列（时 / 分） |
| `cd-tooltip` | 长按 / 点击触发 | hover 触发（带延迟） |

## mode 属性

所有双形态组件都暴露 `mode`：

```vue
<cd-dialog v-model="v" mode="desktop">  <!-- 强制 PC 形态 -->
<cd-dialog v-model="v" mode="mobile">   <!-- 强制移动形态 -->
<cd-dialog v-model="v" mode="auto">     <!-- 默认，跟随视口 -->
```

`auto` 是默认值，依据 `useDevice` 的终端探测结果。

强制指定有两个正当用途：

1. **测试**：不用真机就能验证两种形态
2. **窄容器内嵌 PC 布局**：视口是宽的，但组件被塞进一个窄侧栏里

## 什么时候不该做双形态

`cd-button`、`cd-icon`、`cd-divider` 这类组件是**单形态**的。做双形态要维护两套结构和两套交互，收益必须配得上成本。

判断标准：**这个组件有没有「该平台原生是什么样」的强预期？**

- 选择器：有（手机选东西就是动作面板）→ 做双形态
- 按钮：没有（按钮在哪都长这样）→ 单形态

## 实现要点

双形态不是 `v-if` 两套 DOM 那么简单，三个容易漏的点：

**1. 交互事件要分平台绑定。** 触屏用 `touchstart`，鼠标用 `mousedown`。`cd-stepper` 和 `cd-slider` 都是同时绑两套。

**2. hover 态要分流。** H5 用 `:active`，小程序用 `hover-class`。`cd-button` 内部处理。

**3. 尺寸单位不能是 rpx。** 参见[跨端约束清单](/guide/cross-platform#单位-禁止纯-rpx)。
